# NEEQ 终止挂牌日期语义与 P0 案例审查规则

> 文档性质：设计与审计规则，不是法律意见，也不构成对任何案件实际终止挂牌日期的确认。  
> 适用范围：NEEQ 历史终止挂牌候选案件；当前首批 P0 案例为 836614、838047、430134。  
> 数据安全边界：本规则只指导候选证据审查，不授权自动写入正式生命周期表或 `security_master`。

## 1. 目标与基本原则

NEEQ 结果接口返回的 `delistingDate` 当前统一保留为 `official_result_api_date`（官方结果接口候选日期）。即使来源域名属于全国股转系统，也不能仅凭字段名把它解释为法律上的实际终止挂牌日期。

每一个日期必须同时记录：

- 日期值；
- 日期语义；
- 对应程序节点；
- 证据来源及原文位置/摘录；
- 证据状态；
- 核验结论与核验范围。

不得只保存一个含义不明的 `delisting_date` 来代表整条程序时间线。

## 2. 七类日期的规范语义

| 规范字段 | 含义 | 典型证据 | 不得推导为 |
|---|---|---|---|
| `decision_date` | 有权机构作出终止挂牌决定的日期 | 决定书、正式决定公告；主办券商转述可作辅助证据 | 实际终止日期 |
| `decision_received_date` | 公司或主办券商实际收到决定的日期 | 收到决定公告、送达记录 | 决定作出日期 |
| `conditional_termination_date` | 在未申请复核、复核未获受理等条件成立时适用的预计/条件日期 | 决定公告中的条件条款 | 无条件的实际终止日期 |
| `final_announcement_date` | 最终终止挂牌公告的发布日期 | 最终终止挂牌公告及其发布日期 | 公告所述的生效日期，除非正文明确相同 |
| `actual_termination_date` | 经可靠证据确认的实际终止挂牌生效日期 | 明确记载实际终止生效日的正式公告、决定执行确认或其他权威记录 | 不能由接口日期、条件日期或公告发布日期自动填充 |
| `registration_exit_date` | 中国结算终止登记服务/退出登记完成日期 | 中国结算终止登记服务公告、退出登记凭证 | 自动等同实际终止挂牌日期 |
| `official_result_api_date` | NEEQ 结果接口原始返回日期，保留来源字段语义 | 原始 API 响应、请求时间、响应哈希 | 上述任一法律/程序日期 |

补充规则：

1. `final_announcement_date` 是公告发布日；公告正文中的终止生效日应另记为 `actual_termination_date` 候选，不能混为一列。
2. `registration_exit_date` 是登记服务退出流程日期。除非原始凭证明确说明其法律效力与终止挂牌生效日一致，否则两者必须分开。
3. 若原文只有“自某日起终止挂牌”的条件表述，必须保留条件，不得将其录入为已确认的实际日期。
4. “官方来源”描述来源权威性，不自动证明某个日期字段的语义或真实性；必须核对原文具体表述。
5. `searched_not_found` 只表示记录的检索范围内未找到，不证明公告或登记记录不存在。

## 3. 日期证据等级与核验门槛

建议继续沿用现有证据等级，同时增加语义级审查：

- **直接官方证据**：全国股转系统正式决定/公告、中国结算正式登记记录、发行人正式公告中明确披露的程序事实。
- **官方转述证据**：主办券商公告转述全国股转公司决定。可以支持决定编号、决定日期等被明确转述的内容，但应标记“非决定原件”。
- **可靠二手线索**：媒体、数据库或其他第三方信息，只用于发现线索或辅助交叉验证。
- **未核验线索**：接口字段、搜索摘要、未经读取的附件名单、仅有台账元数据的关系标记。

实际终止日期进入正式生命周期表，至少要求：

1. 证据正文明确指向该证券；
2. 证据明确说明“实际终止挂牌/自某日起终止挂牌”等生效语义，而非条件预测或单纯公告发布日期；
3. 复核、撤销、补充决定等可能改变执行结果的程序已核查，或证据本身明确覆盖最终状态；
4. 证据来源、URL、发布日期、摘录/文件哈希可追溯；
5. 人工审核明确确认日期语义与证券身份；
6. 不存在未解决的关键矛盾。

仅有中国结算退出登记日期时，应先写入独立的 `registration_exit_date` 证据节点；除非文件明确建立两种日期的等价关系，不自动升级为 `actual_termination_date`。

## 4. 三个 P0 案例的日期审查矩阵

### 4.1 836614 奥其斯

| 日期/事项 | 当前记录 | 证据判断 |
|---|---|---|
| 决定日期 | 2019-07-19 | 新时代证券 2019-07-22 公告转述股转系统发〔2019〕2065号；属于官方转述证据，尚未取得决定原件 |
| 条件终止日期 | 2019-07-29 | 主办券商公告明确记载，但是否满足复核条件尚未核实 |
| 接口候选日期 | 2019-09-06 | 保留为 `official_result_api_date`，不得作为实际日期 |
| 2019-984名单 | 附件一背景名单，不在附件二46家正式决定名单 | 不得将2019-07-01视为奥其斯的决定日期 |
| 2019-1071名单归属 | 待核验原始附件 | 台账中的 `formal_decision_company` 元数据不能代替附件核验 |
| 实际终止日期 | 未确认 | 当前没有足以确认实际生效日的直接证据 |
| 退出登记日期 | 未确认 | 尚未取得中国结算退出登记凭证 |

**审核结论：** 保留决定日期和条件日期的证据节点；实际终止日期为空/未确认。不得把2019-09-06写入 `security_master.delisting_date`。

## 5. 对现有 Schema v8 的适配性审查

现有模型已具备大部分必要结构：

- `neeq_termination_case.interface_result_date`：可隔离保存结果接口候选日期。
- `neeq_termination_procedure.event_date` + `date_semantics` + `date_status`：可表达决定、收到决定、条件终止、实际终止、最后交易日、转让开始和退出登记等程序节点。
- `neeq_termination_evidence` 与 `neeq_termination_evidence_link`：可追溯证据及其支持/反驳的程序节点。
- `neeq_termination_evidence_search`：可保留每次检索范围和结果。
- `security_lifecycle_events`：已有决定日期、收到日期、最后交易日、终止生效日期、证据等级及来源字段。

发现的模型缺口/风险：

1. NEEQ `date_semantics` 枚举目前有 `announcement`，但没有单独的 `final_announcement`。若后续要严格区分最终公告发布日期与实际生效日，建议在下一次有明确需求时扩展枚举。
2. 正式 `security_lifecycle_events` 主要依靠 `event_type` 区分语义，未像 NEEQ procedure 一样保存独立的 `date_semantics`。目前可以用不同事件类型表达，但应通过服务层验证事件类型与日期字段的一致性。
3. `security_master.delisting_date` 是无独立语义/证据引用的单一字段，是最容易被错误映射的地方。未完成实际日期审核前不得写入。
4. 目前没有证据表明需要立即新增第9版 Schema。现有 NEEQ 证据台账足以继续调查和保存候选日期；应先补齐服务层规则和测试，再决定是否扩展枚举。

## 6. 服务层应落实的禁止映射规则

以下规则应由后续验证器/测试强制执行：

- `conditional_termination` 节点不得自动生成 `actual_termination` 节点。
- `decision_issued` 或 `decision_received` 不得自动填充实际终止日期。
- `announcement` / `final_announcement` 的发布日期不得自动填充实际终止日期。
- `official_result_api_date` 不得自动填充 `actual_termination_date` 或 `security_master.delisting_date`。
- `transfer_exit` 不得自动等同 `actual_termination`。
- 第三方媒体仅能生成线索或辅助证据，不得单独确认正式实际终止日期。
- 有未解决的复核申请、受理、复核决定或补充决定线索时，不得确认原条件日期已经执行。
- 同一证券存在多个不同日期时，必须保留各自语义，不得采用“最晚日期”或“最早日期”规则自动择一。

## 7. 建议的下一步开发顺序

1. 增加纯函数级日期语义验证器：检查 procedure_type、date_semantics、证据种类和目标事实之间的合法映射。
2. 增加负向测试：确保上述禁止映射均被拒绝。
3. 增加只读审计脚本：扫描 NEEQ 台账和正式生命周期表，报告疑似把接口/条件/公告日期写成实际日期的记录。
4. 对三个 P0 案例继续补充原始证据，不因为模型完成而降低证据门槛。
5. 只有在服务层确实需要表达新的独立日期语义时，再评估 Schema v9。

## 8. 当前安全结论

- 三个 P0 案例实际终止挂牌日期均未确认。
- 本文不写入数据库，不新增正式生命周期事实。
- 不修改 `security_master`，不改变新闻工作流、调度器或推送模板。
- 后续所有正式化操作仍须人工审核和明确授权。
